# Брифинг для Claude Code: продолжение Cross-Chain Bridge Tracer (2026-08-15)

## Как использовать
Вставьте этот файл первым сообщением в новую сессию Claude Code — рабочая
директория `C:\Users\Admin\Desktop\Bridge Tracer` уже содержит весь код,
это git-репозиторий (`git log --oneline` покажет историю). `.env` в корне
проекта уже содержит рабочие `BLOCKSCOUT_API_KEY` и `TRONGRID_API_KEY` —
не в git, но на диске сохраняется между сессиями.

## Текущее состояние: MVP работает end-to-end на реальных данных

Полная цепочка реализована и живо проверена: `bridge_tracer.trace_full_path()`
— TronGrid/LayerZero Scan (депозит на Tron) → LayerZero Scan (мост, включая
Legacy Mesh с промежуточным хабом Arbitrum) → Blockscout Pro (пост-bridge
обход на EVM-сети) → плоский вердикт.

```bash
python3 bridge_tracer.py --start <Tron-адрес> [--start-type address|tx_hash] [--max-hops N]
```

105/105 офлайн-тестов проходят (`pytest -v --ignore=aml/common/tests
--ignore=aml/attribution/tests/test_service.py` — эти два исключения нужны
`POSTGRES_DSN`, который в `.env` указывает на недостижимый с этой машины
docker-internal IP, к задаче трейсера отношения не имеет).

### Ключевые файлы
- `layerzero_tracer.py` — стоп-независимый сопоставитель одного сообщения
  LayerZero (source ↔ destination), включая декодирование реального
  получателя из OFT-payload и обнаружение Legacy Mesh Hop 2 через
  `destination.lzCompose`.
- `bridge_tracer.py` — оркестратор `trace_full_path()`: находит депозит на
  Tron через LayerZero Scan (`messages/wallet`), дочитывает цепочку
  bridge-хопов (Legacy Mesh), затем пост-bridge обход на EVM через
  `evm_adapter`.
- `usdt0_deployments.py` — живой (с диск-кэшем на 24ч) клиент к
  официальному USDT0 Deployments API, реестр Tron-OApp адресов.
- `known_contracts.py` — маленький статический реестр меток (биржи/DEX/
  мосты) для стоп-условий пост-bridge обхода.
- `aml/` — переиспользуемая часть основной AML-платформы (evm_adapter,
  tron_adapter — оба чистые network-адаптеры без знания о мостах).

## Уроки этой сессии (важно не наступить на те же грабли повторно)

Пять реальных багов найдены ТОЛЬКО живым тестированием (не офлайн-тестами
на синтетике) — подробности и как именно каждый обнаружен и исправлен см.
docx раздел 9.6:
1. `pathway.receiver.address` в LayerZero Scan — это адрес общего
   OApp/adapter-контракта, не настоящего получателя; реальный получатель
   зашит в `source.tx.payload` (ABI-декодирование, есть msg-type guard
   0x0002 vs 0x0004).
2. Наивный выбор "следующего хопа" в пост-bridge обходе мог указать на
   перевод ДО прихода средств на высокоактивный адрес — исправлено
   привязкой к времени предыдущего хопа.
3. Несколько Transfer-логов ОДНОЙ транзакции (свопы через 2+ пула)
   ошибочно читались как отдельные хопы — исправлено guard'ом на повтор
   tx_hash.
4. TronGrid-эвристика "прямой перевод на известный bridge-контракт" не
   находила депозиты через промежуточный router/pool-контракт —
   заменена на `layerzero_tracer.find_messages_by_wallet()` (спрашиваем
   у LayerZero Scan напрямую, а не угадываем по TronGrid).
5. Legacy Mesh (USDT0 Transfer Hub): депозит с Tron может идти в 2 хопа
   через Arbitrum как хаб (`destination.lzCompose`) — трейсер
   останавливался на хабе как на финале. Исправлено циклом до
   `MAX_BRIDGE_HOPS=3` в `trace_full_path()`, независимым от `max_hops`
   (глубина пост-bridge обхода на EVM, другая переменная, другая функция,
   другие ключи в `hops[]` — `"leg"` vs `"hop_number"`).

**Методологический урок, который уже дважды здесь подтвердился (Wormhole/Tron
в самом начале работы, потом ещё пять раз выше):** для этой задачи НЕЛЬЗЯ
полагаться на память или даже на "разумно звучащую" эвристику без проверки
на реальных данных. Если что-то похоже на "наверное, это же очевидно
работает так" — проверить живым запросом, прежде чем закладывать в логику.

## Известные, но НЕ исправленные проблемы (на будущее)

- **`tron_adapter.get_transaction_info()` использует, похоже, устаревший
  эндпоинт.** Обнаружено попутно (не является багом bridge_tracer.py — эта
  функция им сейчас не используется): `GET /v1/transactions/{id}` у
  TronGrid стабильно отдаёт 404 даже на заведомо существующий tx_hash.
  Правильный эндпоинт, судя по официальной документации TronGrid,
  вероятно `POST /wallet/gettransactioninfobyid` (или `gettransactionbyid`
  для тела транзакции без receipt) — не проверено и не исправлено, просто
  зафиксировано. Если где-то в будущем понадобится эта функция — сначала
  перепроверить актуальный эндпоинт живым запросом, не чинить вслепую.
- **`evm_adapter/config/chains.yaml` не покрывает все сети, куда реально
  приходит USDT0.** Обнаружено живым Legacy Mesh Hop 2 на xlayer (chain_id
  196) — `_walk_evm()` корректно падает с понятной `ValueError`
  ("chain_id=196 не сконфигурирован"), не тихо врёт, но и не работает.
  Сейчас сконфигурированы: 1, 56, 137, 42161, 10, 8453. Расширять
  chains.yaml — отдельная, не срочная задача (может задеть остальную
  AML-платформу, не только bridge_tracer).
- Один реальный Polygon-адрес (`0x6ba10300f0dc58b7a1e4c0e41f5dabb7d7829e13`
  — похоже, общий Composer-контракт для Hop 2 на Polygon) стабильно
  отдаёт HTTP 500 от Blockscout Pro на `token-transfers` — не наша
  проблема, но если тестируете именно эту сеть/адрес, не удивляйтесь.
