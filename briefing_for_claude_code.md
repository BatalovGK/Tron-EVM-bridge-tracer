# Брифинг для Claude Code: продолжение Cross-Chain Bridge Tracer (2026-08-15)

## Как использовать
Вставьте этот файл первым сообщением в новую сессию Claude Code — рабочая
директория `C:\Users\Admin\Desktop\Bridge Tracer` уже содержит весь код,
это git-репозиторий (`git log --oneline` покажет историю). `.env` в корне
проекта уже содержит рабочие `BLOCKSCOUT_API_KEY` и `TRONGRID_API_KEY` —
не в git, но на диске сохраняется между сессиями.

## Контекст задачи
Тестовое задание на позицию "blockchain analyst" в BitOK: MVP-трейсер,
прокладывающий путь транзакции через кросс-чейн мост (TRON → Ethereum и

раздел 9 (9.1–9.11), актуализирован под сегодняшний день. Если нужен
контекст глубже раздела 9 — читайте сам docx, здесь только сводка.

## Текущее состояние: MVP работает end-to-end на реальных данных

Полная цепочка реализована и живо проверена: `bridge_tracer.trace_full_path()`
— TronGrid + Bridge Contract Registry (депозит на Tron, ОСНОВНОЙ путь,
`bridge_registry.py`), fallback на LayerZero Scan messages/wallet, если
TronGrid ничего не нашёл → LayerZero Scan (мост, включая Legacy Mesh с
промежуточным хабом Arbitrum) → Blockscout Pro (пост-bridge обход на
EVM-сети) → плоский вердикт.

```bash
python3 bridge_tracer.py --start <Tron-адрес> [--start-type address|tx_hash] [--max-hops N]
```

109/109 офлайн-тестов проходят (`pytest -v --ignore=aml/common/tests
--ignore=aml/attribution/tests/test_service.py` — эти два исключения нужны
`POSTGRES_DSN`, который в `.env` указывает на недостижимый с этой машины
docker-internal IP, к задаче трейсера отношения не имеет).

### Ключевые файлы
- `layerzero_tracer.py` — стоп-независимый сопоставитель одного сообщения
  LayerZero (source ↔ destination), включая декодирование реального
  получателя из OFT-payload и обнаружение Legacy Mesh Hop 2 через
  `destination.lzCompose`.
- `bridge_registry.py` — generic Bridge Contract Registry (адрес → сеть/
  протокол/тип/источник+дата провенанса), переиспользуемый не только для
  Tron. Официальные записи из USDT0 Deployments API (все сети сразу) +
  эмпирический слой вручную подтверждённых адресов (сейчас один
  pool/router-контракт на Tron, см. "Второй раунд" ниже).
- `bridge_tracer.py` — оркестратор `trace_full_path()`: находит депозит на
  Tron ДВУХУРОВНЕВО — TronGrid + `bridge_registry.py` как основной путь
  (`_find_tron_bridge_deposit_via_trongrid`), LayerZero Scan
  `messages/wallet` как fallback (`_find_tron_bridge_deposit_via_layerzero_scan`,
  если TronGrid ничего не нашёл в реестре или недоступен) — затем дочитывает
  цепочку bridge-хопов (Legacy Mesh), затем пост-bridge обход на EVM через
  `evm_adapter`.
- `usdt0_deployments.py` — живой (с диск-кэшем на 24ч) клиент к
  официальному USDT0 Deployments API, используется и `bridge_registry.py`
  (официальные записи для всех сетей), и fallback-путём в `bridge_tracer.py`
  (реестр Tron-OApp через `get_tron_oft_contracts()`).
- `known_contracts.py` — маленький статический реестр меток (биржи/DEX/
  мосты) для стоп-условий пост-bridge обхода. НЕ путать с
  `bridge_registry.py` — разные реестры для разных вопросов ("куда трейс
  останавливается" vs "куда приходит депозит В мост").
- `aml/` — переиспользуемая часть основной AML-платформы (evm_adapter —
  чистый network-адаптер без знания о мостах; tron_adapter — теперь
  используется bridge_tracer.py и как сетевой клиент для TronGrid-пути
  (`get_trc20_transfers`), и как чистая утилита адресов для fallback-пути
  (`base58_to_hex`)).

## Уроки этой сессии (важно не наступить на те же грабли повторно)

Пять реальных багов найдены ТОЛЬКО живым тестированием (не офлайн-тестами
на синтетике) — подробности и как именно каждый обнаружен и исправлен см.
docx раздел 9.6:
1. `pathway.receiver.address` в LayerZero Scan — это адрес общего
   OApp/adapter-контракта, не настоящего получателя; реальный получатель
   зашит в `source.tx.payload` (ABI-декодирование, есть msg-type guard
   0x0002 vs 0x0004).
2. Наивный выбор "следующего хопа" в пост-bridge обходе мог указать на
   перевод ДО прихода средств на высокоактивный адрес — исправлено
   привязкой к времени предыдущего хопа.
3. Несколько Transfer-логов ОДНОЙ транзакции (свопы через 2+ пула)
   ошибочно читались как отдельные хопы — исправлено guard'ом на повтор
   tx_hash.
4. TronGrid-эвристика "прямой перевод на известный bridge-контракт" не
   находила депозиты через промежуточный router/pool-контракт —
   заменена на `layerzero_tracer.find_messages_by_wallet()` (спрашиваем
   у LayerZero Scan напрямую, а не угадываем по TronGrid).
5. Legacy Mesh (USDT0 Transfer Hub): депозит с Tron может идти в 2 хопа
   через Arbitrum как хаб (`destination.lzCompose`) — трейсер
   останавливался на хабе как на финале. Исправлено циклом до
   `MAX_BRIDGE_HOPS=3` в `trace_full_path()`, независимым от `max_hops`
   (глубина пост-bridge обхода на EVM, другая переменная, другая функция,
   другие ключи в `hops[]` — `"leg"` vs `"hop_number"`).

**Методологический урок, который уже дважды здесь подтвердился (Wormhole/Tron
в самом начале работы, потом ещё пять раз выше):** для этой задачи НЕЛЬЗЯ
полагаться на память или даже на "разумно звучащую" эвристику без проверки
на реальных данных. Если что-то похоже на "наверное, это же очевидно
работает так" — проверить живым запросом, прежде чем закладывать в логику.

## Второй раунд этой же сессии: разворот детекции депозита (TronGrid снова основной путь)

После первой валидации (105/105, пять багов выше) пользователь запросил
архитектурный разворот пункта 4: TronGrid снова делается ОСНОВНЫМ путём
детекции депозита, LayerZero Scan messages/wallet — понижен до fallback, а
не заменяет TronGrid полностью. Это НЕ откат старого бага под тем же
названием — вот почему:

- Пользователь вручную нашёл на Tronscan конкретный router-контракт
  (`TWPziSAroSacAjDuL52ByQzU86s9mP2gPr`), которого нет в официальном USDT0
  Deployments API. **Прежде чем реализовывать что-либо, факт был
  перепроверен живым запросом** к Tronscan API
  (`apilist.tronscanapi.com/api/transaction-info`) на двух присланных tx
  hash'ах (`800fd19a…82b35`, `85769a68…98729`) — подтверждено: USDT в обеих
  транзакциях доходит до этого адреса и в ТОЙ ЖЕ атомарной транзакции
  пересылается (за вычетом комиссии пула) на официальный OFT
  `TFG4wBaDQ8sHWWP1ACeSGnoNR6RRzevLPt`. Контракт верифицирован на Tronscan
  под именем "OftBridge". Важно: пользователь сам изначально ошибочно
  сослался на "docx раздел 9.6" как источник этого адреса — там его не
  было; это было явно указано пользователю и не принято на веру без
  независимой проверки.
- Вместо возврата к "прямой transfer на единственный жёстко заданный
  адрес" появился `bridge_registry.py` — generic, переиспользуемый реестр
  с явным провенансом на каждую запись (source: `usdt0_deployments_api` /
  `empirical_verified`, дата, а для эмпирических записей — ссылки на
  tx-доказательства). TronGrid-путь сверяется с этим РАСШИРЯЕМЫМ реестром,
  а не угадывает по одному адресу — и LayerZero Scan остаётся полноценным
  fallback'ом для всего, что в реестр ещё не попало.
- **Баг №6, найден тем же методом (живой прогон), в момент внедрения**:
  TronGrid отдаёт `transaction_id` БЕЗ префикса `0x` (голый hex), а
  LayerZero Scan API (`GET /v1/messages/tx/{txHash}`) требует префикс —
  без него отвечает "не найдено" даже для существующего сообщения.
  TronGrid-путь корректно находил депозит, но `find_bridge_crossing()` на
  следующем шаге получал `BRIDGE_MESSAGE_NOT_FOUND` — поймано и исправлено
  ДО сдачи именно потому, что результат был прогнан на реальном адресе, а
  не только на моках.

Тесты выросли с 16 до 20 в `test_bridge_tracer.py` (105 → 109 в целом по
репозиторию): TronGrid-путь на `official_oft` и на `pool_router` записях
реестра, fallback на промах реестра, fallback на ошибку/недоступность
TronGrid.

Оба присланных адреса (`TW37rD2LrsURThJB3ohNztWUUKtJ49KjJb`,
`TMTkbTwMgkPTXngZeZm5tprgTTmbR3sXvn`) прогнаны через полный
`trace_full_path()` живым запуском — оба раза депозит найден TronGrid-путём
(`detection_method=trongrid_registry_match`), путь до конца (Arbitrum
DEX-своп и Binance соответственно) отработал корректно.

Docx обновлён: новый раздел 9.11 с полной историей этого разворота
(включая находку про `0x`-префикс), плюс правки в 9.5/9.8/9.9 (счётчик
тестов, описание пайплайна).

## Известные, но НЕ исправленные проблемы (на будущее)

- **`tron_adapter.get_transaction_info()` использует, похоже, устаревший
  эндпоинт.** Обнаружено попутно (не является багом bridge_tracer.py — эта
  функция им сейчас не используется): `GET /v1/transactions/{id}` у
  TronGrid стабильно отдаёт 404 даже на заведомо существующий tx_hash.
  Правильный эндпоинт, судя по официальной документации TronGrid,
  вероятно `POST /wallet/gettransactioninfobyid` (или `gettransactionbyid`
  для тела транзакции без receipt) — не проверено и не исправлено, просто
  зафиксировано. Если где-то в будущем понадобится эта функция — сначала
  перепроверить актуальный эндпоинт живым запросом, не чинить вслепую.
- **`evm_adapter/config/chains.yaml` не покрывает все сети, куда реально
  приходит USDT0.** Обнаружено живым Legacy Mesh Hop 2 на xlayer (chain_id
  196) — `_walk_evm()` корректно падает с понятной `ValueError`
  ("chain_id=196 не сконфигурирован"), не тихо врёт, но и не работает.
  Сейчас сконфигурированы: 1, 56, 137, 42161, 10, 8453. Расширять
  chains.yaml — отдельная, не срочная задача (может задеть остальную
  AML-платформу, не только bridge_tracer).
- Один реальный Polygon-адрес (`0x6ba10300f0dc58b7a1e4c0e41f5dabb7d7829e13`
  — похоже, общий Composer-контракт для Hop 2 на Polygon) стабильно
  отдаёт HTTP 500 от Blockscout Pro на `token-transfers` — не наша
  проблема, но если тестируете именно эту сеть/адрес, не удивляйтесь.
- **TronGrid-путь детекции депозита (`_find_tron_bridge_deposit_via_trongrid`)
  читает только первую страницу `get_trc20_transfers` (limit=200).** Тот же
  класс ограничения, что у `MAX_EVM_TRANSFERS_PER_PAGE` в `_walk_evm()`: у
  очень активного Tron-адреса релевантный перевод может не попасть на
  страницу — тогда TronGrid-путь молча вернёт `None`, и подхватит fallback
  на LayerZero Scan (не баг, а деградация — результат найдётся, просто
  медленнее). Пагинация не реализована — не было запроса на это, и разумная
  деградация уже есть.
