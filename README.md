# Cross-Chain Bridge Tracer

MVP-трейсер полного пути транзакции через кросс-чейн мост: TRON → LayerZero
(USDT0) → произвольная EVM-сеть.

Единая точка входа — `bridge_tracer.trace_full_path()`:

```
TronGrid + Bridge Contract Registry (депозит на Tron, ОСНОВНОЙ путь,
    bridge_registry.py), fallback на LayerZero Scan (messages/wallet, если
    TronGrid ничего не нашёл в реестре)
    -> LayerZero Scan (сопоставление входа/выхода моста, включая Legacy Mesh
       с промежуточным хабом Arbitrum, до MAX_BRIDGE_HOPS сообщений подряд)
    -> Blockscout Pro (пост-bridge обход исходящих переводов на EVM-сети)
    -> плоский вердикт (final_status / final_chain / final_address / hops / ...)
```

Почему LayerZero, а не Wormhole/другой мост, разбор всех архитектурных
решений и ограничений (включая два разворота логики детекции депозита за
один день — оба по живым данным) — см.
`BitOK_bridge_tracer_architecture.docx`, раздел 9. Здесь — только
практическое "как запустить и проверить".

## Установка

Требуется Python 3.10+ (разработано и проверено на 3.14).

```bash
pip install -r requirements.txt --break-system-packages
cp .env.example .env
# впишите в .env реальный BLOCKSCOUT_API_KEY (обязателен для пост-bridge
# обхода на EVM). TRONGRID_API_KEY опционален — TronGrid работает и без
# ключа (публичный тир, просто медленнее), но раз TronGrid теперь основной
# путь детекции депозита (см. .env.example), ключ рекомендуется.
```

## Как запустить

```bash
python3 bridge_tracer.py --start <Tron-адрес отправителя> [--max-hops N]
# или, если уже есть хэш депозитной транзакции на Tron:
python3 bridge_tracer.py --start <tx_hash> --start-type tx_hash
```

Справка по аргументам (`argparse`, работает "из коробки", ничего отдельно
не реализовано) — `-h`/`--help`:

```bash
python3 bridge_tracer.py --help
```

```
usage: bridge_tracer.py [-h] --start START [--start-type {address,tx_hash}]
                        [--max-hops MAX_HOPS]

Сквозной трейсер пути транзакции: TronGrid, fallback LayerZero Scan (депозит
на Tron) -> LayerZero Scan (пересечение моста) -> Blockscout Pro (EVM)

options:
  -h, --help            show this help message and exit
  --start START         Tron-адрес отправителя или хэш депозитной tx на Tron
  --start-type {address,tx_hash}
  --max-hops MAX_HOPS
```

Одиночный сопоставитель одного хопа моста (без пост-bridge обхода) можно
проверить отдельно:

```bash
python3 layerzero_tracer.py --tx <хэш транзакции LayerZero>
```

## Как проверить

### 1. Офлайн-тесты (без сети, ~5 секунд)

```bash
pytest -v
```

63 теста должны пройти — без флагов-исключений и без внешней инфраструктуры
(никакой реальный сервис, включая PostgreSQL, для тестов не нужен). Все
внешние API замоканы на синтетических ответах, повторяющих реальные схемы,
проверенные живыми запросами — см. докстринги модулей и раздел 9.6
архитектурного документа.

### 2. Живая проверка на реальных данных

Единственный надёжный способ убедиться, что интеграция с живыми API
работает — прогнать на реальном Tron-адресе или tx hash, связанном с
переводом USDT0 TRON → EVM:

```bash
python3 bridge_tracer.py --start <реальный Tron-адрес>
```

Результат можно сверить вручную на [layerzeroscan.com](https://layerzeroscan.com)
(тот же API, на котором работает сам официальный LayerZero Scan) и на
Blockscout соответствующей целевой сети.

## Структура

```
bridge_tracer.py           — оркестратор, trace_full_path()
bridge_registry.py         — generic Bridge Contract Registry (адрес -> сеть/
                              протокол/тип/источник+дата), официальные записи
                              из USDT0 Deployments API + эмпирически
                              подтверждённые вручную (pool/router-контракты)
observed_name_tags.py      — persistent write-through кэш самоуказанных
                              имён адресов (TronGrid account_name / Blockscout
                              Pro name у verified-контрактов) — ЧИСТО
                              информационно, не влияет на маршрут/стоп-условия
                              (см. докстринг модуля, почему это разделено с
                              known_contracts.py/bridge_registry.py)
layerzero_tracer.py        — сопоставитель одного сообщения LayerZero
                              (source ↔ destination), декодирование
                              реального получателя из OFT-payload,
                              обнаружение Legacy Mesh Hop 2
usdt0_deployments.py       — живой (с диск-кэшем на 24ч) клиент к
                              официальному USDT0 Deployments API
known_contracts.py         — статический реестр меток (биржи/DEX/мосты)
                              для стоп-условий пост-bridge обхода
test_bridge_tracer.py      — офлайн-тесты trace_full_path() (27 сценариев)
test_layerzero_tracer.py   — офлайн-тесты find_bridge_crossing()
aml/                       — переиспользуемая часть основной AML-платформы
                              (сужено до реального scope этого задания — см.
                              aml/README.md; исходная платформа с Attribution
                              Engine/Flow Tracer/agent tool-calling живёт в
                              отдельном проекте, здесь оставлены только сетевые
                              адаптеры, которые реально использует bridge_tracer.py)
  evm_adapter/                клиент к Blockscout Pro (rate limiting, кэш)
  tron_adapter/                клиент к TronGrid (используется bridge_tracer.py
                                как основной путь детекции депозита — сверка
                                исходящих TRC-20-переводов с bridge_registry.py
                                — плюс утилита base58_to_hex для fallback-пути)
  common/                      secrets.py — единая точка чтения API-ключей,
                                используется обоими адаптерами
BitOK_bridge_tracer_architecture.docx — архитектурный документ (полная
                              история решения, разделы 1–8 — общий подход
                              к разным типам мостов, раздел 9 — реализация)
briefing_for_claude_code.md — журнал разработки для передачи между сессиями
```

## Известные ограничения (сознательные, MVP)

- **Обнаружение депозита** — двухуровневое: TronGrid сверяется с
  `bridge_registry.py` (официальные OFT-адреса из USDT0 Deployments API +
  небольшой эмпирический список вручную подтверждённых pool/router-
  контрактов); если совпадения нет — fallback на LayerZero Scan
  messages/wallet, который сам ограничен реестром известных Tron-OApp того
  же USDT0 Deployments API (сейчас один — USDT0 OFT на Tron). Депозит через
  ДРУГОЙ протокол/мост LayerZero трейсер не найдёт ни одним из путей.
- **Пост-bridge обход на EVM** — линейный "один хоп = самый ранний подходящий
  по времени исходящий ERC-20-перевод", НЕ amount-aware taint-трейсинг, полностью
  автоматический (нет параметра для ручной подсказки/уточнения хопа — только
  реестр-чек ПОСЛЕ выбора кандидата, см. `_walk_evm`). До `max_pages_per_hop`
  страниц Blockscout на хоп (по умолчанию 4, параметр с дефолтом, не хардкод)
  — если и они не дотягиваются до подходящего перевода, а у Blockscout ещё
  остаются более старые страницы, трейс честно возвращает
  `SEARCH_DEPTH_EXCEEDED` ("не хватило глубины"), а не молча выдаёт
  `RESTED_AT_ADDRESS` ("дальше некуда идти") — эти два статуса теперь
  различаются.
- **«Earliest-after-arrival» результат нестабилен между запусками — и это НЕ
  ограничено патологически высокочастотными адресами.** Обнаружено живыми
  повторными прогонами в этой сессии в ДВУХ разных по природе формах:
  1. *Из-за исчерпания глубины пагинации* — адрес с частотой ~1 исходящий
     перевод/8 секунд (разница между прогонами 4.5 часа): `max_pages_per_hop=4`
     (200 записей ≈ 26 минут его активности) не успевал докрутить до реально
     самого раннего подходящего перевода — трейс дал другой (более поздний,
     но всё ещё технически "самый ранний из видимого сейчас") результат.
     Увеличение `max_pages_per_hop` только отодвигает порог, не устраняет его
     для патологически активных адресов.
  2. **Более серьёзный случай — БЕЗ какого-либо исчерпания глубины
     пагинации.** Обнаружено на умеренно активном адресе
     (`TAfpoKQJfPiLa9AAkEk8CogM9GBTLBeoqH` →
     `0x07ae8551be970cb1cca11dd7a11f47ae82e70e67`): два прогона одного и того
     же адреса с разницей ~15 МИНУТ дали два полностью несвязанных hop 1 —
     разный токен (USDC ~4065 vs USDT ~1014), разная сумма в разы, разный
     получатель, разный tx_hash (`0xfaff572a...` в 00:23:23 vs
     `0x89dda4a0...` в 04:19:11). Оба технически проходят критерий отбора
     ("исходящий + не раньше прихода моста") — просто к моменту второго
     прогона появился новый подходящий кандидат, который стал "самым ранним"
     вместо прежнего. Ни один из двух не гарантированно связан с
     трейсящимися деньгами: выбор хопа не amount-aware и не token-aware (см.
     пункт про `dex_swap` выше) — "самый ранний подходящий по
     направлению/времени" эвристика, не доказательство преемственности
     средств, и она может указывать на два совершенно разных перевода на
     ЛЮБОМ умеренно активном адресе, не только на экстремальных ~1/8сек.

  **Практическое следствие для комплаенс-задач:** результат — снимок
  состояния на момент запроса, а не окончательная истина. Совпадение при
  повторных прогонах означает только, что с момента трассировки на адресе
  пока не появилось нового подходящего перевода в это окно — не гарантию,
  что так будет всегда: результат в принципе может снова смениться, если
  позже появится ещё один подходящий перевод (в т.ч. более ранний, чем уже
  найденный) или если Blockscout задним числом доиндексирует данные.
  "Стабилизировался при повторных прогонах" — это НЕ признак окончательной
  надёжности, только отсутствие изменений в наблюдаемом окне на данный
  момент.
- **Blockscout Pro на Polygon (chain_id=137) наблюдался ненадёжным** в этой
  сессии (HTTP 500 / network timeout) — проверено отдельно: НЕ привязано к
  конкретному адресу и НЕ коррелирует с объёмом его данных (падает и на
  высокоактивном, и на почти пустом адресе; тот же высокоактивный адрес на
  Ethereum отрабатывает чисто). Похоже на общую нестабильность именно
  Polygon-маршрута Blockscout Pro, не баг адаптера — но системный риск для
  ЛЮБОГО запроса на этой сети, не единичный случай одного адреса.
- **Детекция DEX-свопа (`dex_swap`) ловит только один структурный паттерн** —
  несколько Transfer-логов ВНУТРИ ОДНОЙ И ТОЙ ЖЕ tx (адрес получил один токен
  и в той же атомарной транзакции отправил другой). Если конвертация актива
  происходит через раздельные транзакции (например, solver/router получает
  один актив в одной tx и выплачивает другой в соседней, даже в том же
  блоке) — трейсер это не распознаёт и продолжает обход уже по новому
  токену, как будто это прямое продолжение прежних средств. Обнаружено
  живым сравнением двух прогонов в этой сессии: прогон A
  (`TXSs47LKWcxf4Kq2CgBpmLkcgv2RTFmfkq`, hop 3, USDT→USDC внутри одной tx
  `0x1d05746e...`) — пойман, `RESTED_AT_CONTRACT`/`dex_swap`; прогон B
  (`TGrFwL89cV4gAokzHsJZaM5YYYxmDRfQjN`, hop 7, USDT→DKA между двумя разными
  tx одного блока — приход `0xdc56d745...`, уход уже `0xe48a1bfc...`) — НЕ
  пойман, трейс продолжился дальше по DKA до hop 8. Не amount-aware в
  принципе (см. пункт про пост-bridge обход выше) — выбор следующего хопа не
  смотрит на токен вообще, только на направление и время; общий детектор
  свопа (не только same-tx паттерн) вне scope MVP.
- **Второй (независимый) мостовой переход после первого не резолвится** —
  трейсер честно останавливается на bridge-контракте (`RESTED_AT_CONTRACT`,
  `contract_type: "bridge"`), а не идёт дальше. Обнаружено живым запуском в
  этой сессии (`TRhiS9eShff2SLnj2oFbkRdYeftnMS9dHS`): leg 1 (TRON→Arbitrum)
  через `compose_status: SUCCEEDED` автоматически триггерит leg 2
  (Arbitrum→xlayer, тот же LayerZero-переход, через compose-вызов) — это
  уже поддержано, — но финальный адрес на xlayer сам оказался USDT0
  OFT-контрактом (`bridge_registry`), и на этом трейс остановился. Причина:
  `MAX_BRIDGE_HOPS`-цикл в `trace_full_path` резолвит один конкретный
  LayerZero-паттерн (Legacy Mesh, до 2 хопов сообщений одного и того же
  перехода) и полностью завершается ДО начала EVM-обхода (`_walk_evm`);
  обнаружение bridge-контракта внутри `_walk_evm` — независимый механизм,
  специально сделанный как STOP (не тащить исходящие переводы с самого
  OFT-контракта как будто это кошелёк пользователя), а не как триггер для
  повторного входа в мост. Полноценный рекурсивный мульти-bridge трейсинг
  (в том числе через другие протоколы, не только LayerZero, если на xlayer
  стоит другой мост) — отдельная задача вне текущего scope.
- **`observed_name`/`observed_name_source` в результате** — самоуказанное
  имя адреса (TronGrid `account_name` для депозитора, Blockscout Pro
  `name` для verified-контрактов на финальном EVM-адресе), с persistent
  write-through кэшем (`observed_name_tags.py`). Проверено живым запросом:
  ни Blockscout Pro (`public_tags`), ни TronGrid/Tronscan не отдают
  МОДЕРИРУЕМУЮ бизнес-категоризацию (биржа/мост/DEX) программно — только
  самоуказанные имена, которые НЕ используются как основание для
  стоп-условия (сознательное решение — самоуказанное имя можно подделать,
  небезопасно для комплаенс-инструмента; см. докстринг модуля).
- **`aml/evm_adapter/config/chains.yaml` не покрывает все сети**, куда может
  прийти USDT0 (сконфигурированы: Ethereum, BNB Chain, Polygon, Arbitrum,
  Optimism, Base). На неконфигурированной сети `_walk_evm()` падает с понятной
  `ValueError`, не тихо врёт.
- **Не-EVM целевые сети** (Solana, Sui, Aptos, TON и др.) — трейс корректно
  останавливается на точке выхода из моста (`RESTED_AT_ADDRESS`), дальнейший
  обход вне scope MVP (нужен отдельный network adapter под конкретную сеть).
- `aml/tron_adapter.get_transaction_info()` использует, похоже, устаревший
  эндпоинт TronGrid (стабильно отдаёт 404) — не используется bridge_tracer.py,
  зафиксировано на будущее в `briefing_for_claude_code.md`.

## Что не реализовано (сознательно, следующий шаг)

`briefing_for_claude_code.md`.
